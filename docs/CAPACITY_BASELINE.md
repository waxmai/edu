# 容量与稳定性基线

## 目标

正式 SaaS 上线前，至少需要形成一份可复用的容量基线，而不是只依赖单次 smoke 成功。

当前项目建议按下面三层口径做稳定性验证：

1. **链路正确性**
   - `make smoke-e2e`
   - 覆盖登录、改密、会话治理、RBAC、logout、恢复链路
2. **核心并发正确性**
   - `./scripts/loadtest_core_api.sh`
   - 覆盖排课冲突、课包扣减、缴费与关键写链路的一致性
3. **容量基线留档**
   - 记录并发数、成功率、p95、p99、错误率、数据库 CPU/连接数、慢 SQL 样本

## 当前建议基线场景

### 场景 A，登录与会话
- 登录
- refresh token rotation
- logout / logout-all
- 密码恢复 start / reset

重点观察：
- 失败率
- 平均耗时 / p95 / p99
- 锁定策略是否误触发
- 恢复失败事件是否被正确落盘与聚合

### 场景 B，教务核心写链路
- 新增学员
- 新增课时包
- 新增缴费
- 新增排课
- 调课 / 补课 / 请假
- 标记 completed 触发课时扣减

重点观察：
- 并发下是否出现重复写入
- 排课冲突保护是否失效
- 课时扣减是否出现负数 / 双扣
- 事务超时与锁等待是否明显升高

### 场景 C，多租户与套餐边界
- 多机构并发新增账号
- 多机构并发新增校区
- 订阅状态为 `expired/past_due/suspended` 的关键写链路拒绝率
- 配额逼近上限时的行为一致性

重点观察：
- 是否存在跨机构串写
- 限额是否后端强约束
- 拒绝错误码与文案是否稳定

## 建议留档字段

每次压测/回归后至少记录：

- 时间
- 环境
- Git commit
- 数据规模
- 并发数
- 持续时间
- 成功率
- p50 / p95 / p99
- 错误数与错误类型
- 主要慢 SQL
- 结论与是否可发布

## 数据增长治理建议

下面几类数据需要尽早形成生命周期策略：

- `auth_session`
- `auth_recovery_challenge`
- `auth_recovery_audit`
- `logs/alerts.ndjson`
- `logs/recovery-alerts.ndjson`
- 审计导出文件

当前默认建议：

- 告警 ndjson：30 天保留，4MB 触发截尾轮转，最近 5 份归档保留
- 恢复失败日志：同上
- 会话与恢复审计：按业务合规要求另行制定归档策略

## 上线前最低要求

- 至少完成一次 `loadtest_core_api.sh`
- 至少完成一次接近真实数据量的 smoke + 人工点击验收
- 至少完成一次数据库备份恢复演练
- 至少形成一份容量基线留档
